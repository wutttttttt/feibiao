# 借入单的货品进入方式

对象：`docs/飞彪对标分析.md` 中 P0 第 1 项「借入/借出双向单据」。
结论前置：**凡是物理上到了你摊位、会参与盘点的货，都必须逐件建档成 `Good`；借入单本身只承载"批次"维度的事实，不承载货品本体。**

## 一、先纠正一个现有缺陷

`Good.returnedUpstreamAt` 目前是终态标记，`returnUpstream()` 写入后，这件货在所有后续判断里都被排除：

| 位置 | 判断 |
|---|---|
| `moveLocation` | `g.returnedUpstreamAt` 非空则拒绝调位置 |
| `createLoan` | 非空则拒绝对外拿货 |
| `createSale` | 非空则拒绝成交 |
| `createStocktake` | 快照查询排除 `returnedUpstreamAt != null` |
| `returnUpstream` 自身 | 要求 `ownershipKind='CONSIGN' && occupancy='FREE' && holderKind='MERCHANT'` |

结果：同一件货"货主送来 → 卖不掉退回 → 再送来"必须重新录一件新货，**货号重新生成、旧条码标签作废、历史断成两截**。寄售业态里这是高频动作，不能每次新建。

改法（推荐）：把 `returnedUpstreamAt` 当"当前是否已退还"的可逆状态，新增反向动作 `receiveUpstreamAgain()`：

```
holderKind: PARTNER -> MERCHANT
holderPartnerId: null
locationId: 指定位置
occupancy: FREE
returnedUpstreamAt: null
custodianUserId: actor.id
InventoryEvent.action = 'RE_RECEIPT'
```

货号、条码、照片、历史流水全部保留，重新收货一次即可。这是一条 migration 都不需要的纯逻辑改动，建议先做。

## 二、为什么不用现有的 `Loan` 表反向复用

`Loan`/`LoanItem` 的字段语义是单向的：`currentHolderPartnerId`、`responsiblePartnerId` 指的都是**外部持有人**，`returnLoanItem`、`transferLoanItem` 都建立在"货在外面"这个前提上。反向复用会让每个查询和状态判断双义化，修改面远大于新建一张表。

而且借入的"货品本体事实"其实已经在 `Good` 上了：`ownershipKind='CONSIGN'`、`ownerPartnerId`、`sourcePartnerId`、结算方式快照（`settlementType`/`settlementFixedCents`/`settlementRateBp`/`ruleVersion`）。

**缺的只是批次维度的事实：这批货一起到的、谁交的、什么时候到期、当场认可了什么状态。** 这才是借入单要记录的东西。

## 三、数据模型

### 新增表

```prisma
model Intake {
  id           String   @id @default(uuid())
  merchantId   String
  number       String                      // 单号 SH-xxxx，复用 docNo('SH')
  partnerId    String                      // 来源货主 / 上游
  kind         String                      // CONSIGN 寄售收货 | BORROW 临时借入 | PURCHASE 采购入库
  status       String   @default("DRAFT")  // DRAFT 待收货 | RECEIVED 已收货入库 | VOIDED 作废
  receiverName String                      // 货主那边的实际交货人
  dueAt        DateTime?                   // 约定归还 / 结算日，逾期预警的源头
  handedAt     DateTime?
  note         String?
  actorId      String
  createdAt    DateTime @default(now())
  items        IntakeItem[]
  @@unique([merchantId, number])
  @@index([merchantId, partnerId, kind])
  @@index([merchantId, dueAt, status])
}

model IntakeItem {
  id            String   @id @default(uuid())
  merchantId    String
  intakeId      String
  intake        Intake   @relation(fields: [intakeId], references: [id])
  goodId        String
  good          Good     @relation(fields: [goodId], references: [id])
  lineNo        Int                        // 对应货主清单的行号，便于核对
  declaredCents BigInt?                    // 货主报价 / 来货底价
  conditionNote String?                    // 收货当场认可的外观状态
  receivedAt    DateTime?
  returnedAt    DateTime?                  // 单件还回上游的时间
  @@index([merchantId, intakeId])
  @@index([merchantId, goodId])
}
```

> 单件到期日默认继承 `Intake.dueAt`；确有个别件不同期限时再给 `IntakeItem` 加 `dueAt`，第一版不在 `IntakeItem` 上冗余。

### `Good` 不需要加新字段

现有字段已经够：来货时的状态变化写 `InventoryEvent(referenceType='INTAKE', referenceId=intake.id)`，`sourcePartnerId` 记来源，`creating 时的结算快照`由 `createGood` 已有的逻辑完成。

## 四、货品进入系统的三条路径

| 路径 | 适用场景 | 动作 |
|---|---|---|
| **A. 引用已建档货品** | 以前收过、退回去又被同一货主送回来；或已手工录好的货 | 传 `goodIds`，只生成 `IntakeItem` 并刷新持有状态，不重复建 `Good` |
| **B. 单内批量新建** | 一次性收几十件、系统里还没有 | 明细行 → 逐件 `createGood(ownershipKind='CONSIGN', ownerPartnerId=货主)` → 生成 `Good` + `IntakeItem` → 可立即整批打印标签（`/labels/[id]` 已支持） |
| **C. 表格导入后挂单** | 货主发来 Excel/CSV 清单 | 现有 `ImportBatch` 预览 → 校验 → 生成 `Good` 与 `IntakeItem`，等于路径 B 的批处理 |

三条路径最终落到同一个状态：

```
ownershipKind        = CONSIGN
ownerPartnerId       = 货主
currentOwnerKind     = PARTNER          // 货权始终不属于我
currentOwnerPartnerId= 货主
holderKind           = MERCHANT         // 实物在我手上
locationId           = 指定位置
occupancy            = FREE             // 允许立刻被拿货
InventoryEvent.action= 'INTAKE_RECEIPT'
```

## 五、必须守住的七条规则

1. **逐件建档，不按数量**。收 30 件必须生成 30 行 `Good`。一物一码、单件结算、单件货损、盘点全部依赖件级数据；做成"批次 + 数量"会在第一次退货或盘亏时崩掉。
2. **收货与入库分两步**。`DRAFT` 时只是清单，`RECEIVED` 才把 `holderKind` 置为 `MERCHANT`、`occupancy` 置为 `FREE` 并写流水。货主清单与实际到货经常不一致（少发、串号），必须留一次逐件核对确认的动作。
3. **结算规则在收货瞬间锁定**。从 `Partner.settlementType/RateBp/FixedCents` 带入 `Good` 并记 `ruleVersion`，事后改合作方规则不污染这一批。`createGood` 已经是这个逻辑，路径 B/C 直接复用即可。
4. **借入不产生应付**。应付在 `createSale` 里成交时才生成 —— 这条现有逻辑是对的，不要改。
5. **收货不占位**。`occupancy` 保持 `FREE`，允许立即开立拿货单。
6. **货主报价不进 `costCents`**。落 `IntakeItem.declaredCents`；若同时要写我方售价/底价，用 `askingCents` 与 `floorCents`，并由 `cost` 权限保护。
7. **退还走现有 `returnUpstream` 的批量版**。仍是"在手、未成交、对方在库"三条件，成功后把 `IntakeItem.returnedAt` 写上，逾期未还的按 `Intake.dueAt` 进预警列表。

## 六、实施顺序

| 步骤 | 内容 | 依赖 |
|---|---|---|
| 1 | 新增 `receiveUpstreamAgain()`，修 `returnedUpstreamAt` 的可逆问题 | 无，可直接做 |
| 2 | `schema.prisma` 加 `Intake` / `IntakeItem`，`Good` 加反向关系，生成 migration | 无 |
| 3 | `business.ts` 增加 `createIntake`（支持路径 A/B）、`receiveIntake`、`voidIntake`、`returnIntakeItem` | 步骤 2 |
| 4 | `api/v1/[...path]/route.ts` 增加 `/intakes`、`/intakes/:id/receive`、`/intake-items/:id/return` 路由 | 步骤 3 |
| 5 | `/api/import` 增加 `kind=intake`，走路径 C | 步骤 3 |
| 6 | 前端：收货单列表 / 新建（带明细表格）/ 收货核对；小程序保持只读 + 收货核对 | 步骤 4 |

## 七、尚未确认、需要摊主拍板的业务口径

- 寄售货在你手上期间产生保管责任，若在你摊位丢失/损坏，按什么价赔：货主报价、成交净额、还是另行约定。
- 借入到期未还是自动续期，还是生成催还待办并锁定该货不可再外借。
- 收货当场把外观瑕疵记进 `Good.conditionNote`（全局）还是只记 `IntakeItem.conditionNote`（本次），退货扯皮时以哪个为准。推荐以 `IntakeItem.conditionNote` 为准，因为它有时间戳和交货人。
