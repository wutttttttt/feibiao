## 一、项目概况

- **业务主线**：上游借入收货 → 逐件核对入库 → 客户借出（拿货单）→ 逐件归还/成交 → 登记收款核销 → 寄售上游付款 → 对账。拿货只改变持有与责任，成交才形成应收与寄售应付；客户款收齐才允许付上游。
- **角色**：老板（OWNER，全权限）/ 员工（STAFF，细粒度权限 + 按客户授权 customerIds）/ 收银。
- **已有质量资产**：31 项自动化测试通过（业务 13 + 小程序 13 + 解析 3 + 标签 2）；HTTP 级 smoke 测试覆盖导入预览/盘点/货损/成本隔离/跨商家拒绝；备份恢复已演练（28 张业务表数量一致、图片 SHA-256 逐一比对）。
- **已知边界**（docs/验收记录.md）：小程序用 touristappid，从未编译/真机/提审；正式公网部署与异机备份未执行；真机扫码效果未验收。

### 2.4 审查确认的安全亮点（相对同类项目的优势）

- **租户过滤纪律极佳**：逐接口核对所有 findFirst/update 的 where 子句，业务 API 100% 带 merchantId（含 path 参数 id 的归属验证，如 `business.ts:10-14` lockGood、`route.ts:129` 权限更新限定 STAFF+tenant）
- 无字符串拼接 SQL（唯一 $queryRaw 为标签模板参数化）
- 并发控制严谨：Serializable 隔离 + SELECT FOR UPDATE + version 乐观锁；P2034 冲突处理；幂等键事务内原子落库
- 金额全程 BigInt cents，money() 正则 + 上限校验，比例结算四舍五入正确
- CSV 导出公式注入防护；导入表头原型污染防护
- 分享 token 256-bit 随机 + SHA-256 存储；员工密码 ≥12 位 + bcrypt cost 12；cookie httpOnly+sameSite+secure；Bearer 限定小程序 token
- React 全程转义，无 dangerouslySetInnerHTML

## 三、多客户运营差距分析（产品视角）

**核心发现：数据模型天然按商家隔离**——每张业务表都有 merchantId，"接口查询和写入均限定商家"（docs/数据库与业务规则.md），且验收记录第 12 项已验证"跨商家业务访问被拒绝"。**多租户的数据隔离骨架已在，缺的是租户生命周期管理（开通/计费/停用），不是隔离本身。**

| 维度 | 现状 | 差距与建议 |
|---|---|---|
| **A1 客户开通** | `bootstrap-owner.ts` 强制"仅完全空库可初始化"；老板账号由运维手工跑脚本创建。无注册页、无试用、无购买入口；开通成本 30-60 分钟/客户 | 两步走：① 半自动开通（1-2 周）——运营内部页面输入摊主名/手机号/密码 → 自动建 merchant+owner+默认位置；② 自助试用（1-2 月）——官网落地页 + 手机号注册 + 14/30 天试用（`scripts/seed.ts` 演示货逻辑可复用），收款先走人工 |
| **A2 客户成功** | CSV/XLSX 导入有预览校验（货品/合作方/期初/未结拿货四类）；照片须逐件补拍；无新手引导、无 FAQ | 冷启动是最大流失点：首批"上门代录入 200 件货"作为成交动作；P1 做小程序批量拍照工作流（单件建档 2 分钟→40 秒）；P0 写"三天上手"文档（成本极低） |
| **A3 商业化** | 完全无计费概念（无 Plan/Subscription 模型），第一版边界明确排除在线支付 | 按摊位**年订阅**，试探区间 **¥600-1500/年**；首发"创始客户 ¥399 终身价"换口碑；地推现场收款（微信收款码+手工台账），第二阶段再上订单系统；**不做免费版**（小微摊主付费意愿两极分化，免费版拖死客服） |
| **A4 运营后台** | 零——无客户列表、开通/停用、用量统计、客服工具、公告 | 最小后台（P0）：客户列表（状态/到期日/货品数/最近活跃，基于 AuditLog）+ 一键开通/续期/停用（冻结登录，数据保留 90 天）+ "以客户身份只读查看"客服排查 + 批量公告横幅。实现：新增 `/api/admin` 分区 + OPERATOR 只读角色，复用现有权限体系 |
| **A5 产品形态** | 单摊主单服务器；小程序登录页偏运维向（要求填服务器地址） | 网页：统一域名登录页输"摊主号"；小程序：**一套 AppID** + 摊主号/手机号登录（每客户独立小程序需 N 个主体资质，明确不做） |

## 五、多客户技术路线

### 5.1 路线对比

| 维度 | (a) 每客户独立部署 | (b) 单实例多租户 SaaS |
|---|---|---|
| 数据隔离 | 最强（独立 DB + 独立图片目录） | 逻辑隔离（merchantId，代码已达标但爆炸半径大） |
| 代码改动 | 零 | 需改造（见 5.2） |
| 运维成本 | O(N)：N 套 VM/备份/证书/更新 | O(1) 实例 + 平台设施一次性投入 |
| 小程序适配 | **硬伤**：微信合法域名要 HTTPS+ICP 备案、有数量上限与修改频控（待验证具体额度），子域名会耗尽配额 | 最优：单一域名 + 一个小程序 |
| 故障影响 | 单客户故障不扩散 | 一损俱损，需多实例+探活 |
| 适配阶段 | ≤10 客户、本地高客单价上门服务 | 20+ 客户、标准化远程销售 |

### 5.2 SaaS 化的代码级改造前提（已审计确认）

1. **`User.login` 全局唯一**（`prisma/schema.prisma:33`）→ 必须改 `@@unique([merchantId, login])` + 登录时商户选择（摊主号/邀请码）。**这是 schema 层唯一的多租户硬伤**
2. 开通流程缺失：bootstrapOwner 强制空库，需新增受控开通 API
3. 其余覆盖良好：media 按 merchantId 分目录✓、幂等键含 merchantId✓、分享表带 merchantId✓、跨租户侧信道无（UUID 不可枚举）
4. 性能债：列表 take 100-300 无分页、dashboard 全表扫描、单进程 + Serializable 事务——多租户并发必须先压测 + 分页 + PgBouncer

### 5.3 推荐：分阶段混合路线

**短期（≤10 客户）走独立部署，用容器化+自动化把边际成本压到最低；中期（10-50 客户）切 SaaS。**

理由：代码租户基础远好于同类项目，SaaS 改造量可控（主要 login 模型+运营设施）；但运营设施（监控/计费/合规）从零起步，先用独立部署积累真实客户反馈，避免过早平台化；小程序域名硬约束使"一域一户"在 10+ 客户后不可持续。

## 八、商业化与 GTM 建议

1. **路径**：不做线上投放，走瑞丽市场地推——姐告玉城、德龙珠宝夜市等档口集中区，每天扫 20 家。话术锚点用现有优势：**"成交/交付/收款三分离、客户款收齐才允许付上游、每次变动留痕"**（账目纠纷最值钱的点）。飞彪面向直播供应链大商户，摊主级市场存在服务真空。
2. **成交动作**：现场演示（小程序扫码拿货 30 秒出单）→ "帮您把现有货录进去"（代录入 200 件）→ 收首年年费 → 拉微信服务群。
3. **里程碑**：M1（1 个月）10 家付费/试用；M2（3 个月）累计 50 家 + 流失归因；M3（6 个月）150-200 家时评估跨市场复制。首批渗透 100-300 家年营收约 6-45 万元，先验证再扩。

## 九、总体结论

1. **翠账的工程底盘是资产不是负债**：账务严谨性不弱于行业头部（三分离核销、寄售应付门控、乐观锁+Serializable、审计、幂等设计），且有完整测试与备份演练体系。这在小团队项目里罕见，意味着"能不能安全地做"的答案基本是肯定的。
2. **真正的风险集中在三处**：① 幂等键前端缺陷（直接资损）；② 账号生命周期（无改密、无 token 撤销）；③ 运维基础设施（无监控、无异地备份）——全部可在 2-3 周内修复。
3. **从单摊主到多客户的缺口不是代码质量，是结构性的运营能力**：开通、计费、后台、客服、合规资质。建议按"阶段 0 修安全 → 阶段 1 独立部署+地推验证 → 阶段 2 SaaS 化"的节奏推进，先在瑞丽本地把付费漏斗跑通，再决定平台化投入。
